1. Contexto e Objetivo da Atividade

Esta atividade exercita, na prática, a aplicação da Arquitetura Hexagonal (Ports and Adapters), concebida por Alistair Cockburn e aprofundada nas aulas de princípios e padrões de arquitetura (Clean Architecture & Onion). O objetivo primordial é proteger o núcleo de domínio e os casos de uso de detalhes externos, como transporte HTTP (Express), banco de dados e frameworks.

A funcionalidade implementada é a Solicitação de Crédito para Empreendimento Solidário (serviço S4 do Banco Comunitário), permitindo que coletivos, cooperativas e microempreendimentos locais registrem solicitações de crédito produtivo a juros zero. A solução segrega explicitamente Driving Adapters, Input Ports, Use Cases, Domain Entities, Output Ports e Driven Adapters com persistência real em banco de dados relacional.

3. Detalhamento Estrutural dos Elementos Hexagonais

Papel Hexagonal Classe / Interface Responsabilidade Técnica e Regra de Negócio
Driving Adapter
(Adaptador Primário)		 SolidarityCreditController Recebe a requisição HTTP (Express) em POST /credit/solidarity, realiza a validação de presença e tipos primitivos, delega a execução diretamente para o contrato da Input Port e mapeia o resultado para HTTP 201 Created ou erros padronizados.
Input Port
(Porta Primária)		 CreateSolidarityCreditApplication Contrato puro em TypeScript (interface) que declara o método execute(input: CreateSolidarityCreditInput): Promise<CreditRequestDto>. Não possui dependência de HTTP, Express, Headers ou JSON.
Use Case
(Orquestrador)		 CreateSolidarityCreditUseCase Implementa a Input Port. Converte valores em centavos via Money, instancia o empreendimento solidário, aciona as regras de domínio para criar a solicitação de crédito, persiste por meio da Output Port e projeta o DTO de retorno com taxa de juros calculada (0%).
Domain Entities
(Entidades Centrais)		 CreditRequest
SolidarityEnterprise
Money 		CreditRequest: Valida valor positivo, teto de microcrédito solidário comunitário (R$ 15.000,00), prazo em parcelas (1 a 36 meses), descrição da finalidade e ciclo de vida (PENDING, APPROVED, REJECTED).
SolidarityEnterprise: Representa o coletivo produtivo, bairro/área de atuação e validação de elegibilidade comunitária (isEligible()), bloqueando especulação financeira ou atividades não solidárias.
Output Port
(Porta Secundária)		 CreditRequestRepository Interface que define operações de persistência necessárias à aplicação: save(request), findById(id), listAll() e findByEnterpriseName(name). O domínio desconhece onde e como os dados são gravados.
Driven Adapter
(Adaptador Secundário)		 SqliteCreditRequestRepository
InMemoryCreditRequestRepository 		SqliteCreditRequestRepository: Driven Adapter oficial com persistência real em banco de dados relacional SQLite (via módulo nativo node:sqlite do Node.js), criando a tabela credit_requests e executando comandos SQL com integridade.
InMemoryCreditRequestRepository: Adapter em memória utilizado para testes de unidade e isolamento sem I/O.
Fonte de Dados SQLite (community_bank.sqlite) Banco de dados relacional em arquivo local, garantindo armazenamento persistente entre reinicializações da API com transações ACID.

4. Fluxo Completo de uma Requisição (Passo a Passo)

  1. Entrada HTTP: O cliente (aplicativo ou terminal via curl) envia um POST /credit/solidarity contendo no corpo da requisição: 
    {
  "enterpriseName": "Mulheres Rendeiras da Lagoa",
  "communityArea": "Vila Mangueira",
  "activityType": "Artesanato e Renda de Bilro",
  "membersCount": 6,
  "amount": 2500.00,
  "purpose": "Aquisição de linhas de algodão puro e almofadas de bilro",
  "installments": 10
}
  2. Driving Adapter (Controller): SolidarityCreditController intercepta a requisição, valida campos básicos (ausência de strings vazias, valores numéricos válidos) e empacota os dados em um DTO simples CreateSolidarityCreditInput.
  3. Transição pela Input Port: O controller chama this.createCreditPort.execute(input). Como o controller só depende da interface da porta, ele ignora os detalhes de implementação do caso de uso.
  4. Coordenação no Caso de Uso: CreateSolidarityCreditUseCase converte o valor em reais para centavos inteiros (Money.fromReais(2500) = 250000 centavos) para imunidade contra erros de ponto flutuante IEEE 754.
  5. Validação de Domínio: A entidade SolidarityEnterprise valida o coletivo e a elegibilidade da atividade. Em seguida, a factory de domínio CreditRequest.create(...) assegura que o valor não ultrapassa R$ 15.000,00, as parcelas estão entre 1 e 36 meses e o status inicial é PENDING.
  6. Persistência pela Output Port: O caso de uso invoca await this.repository.save(creditRequest).
  7. Gravação no Driven Adapter: SqliteCreditRequestRepository recebe a entidade, mapeia os atributos para a tabela SQL relacional e persiste no arquivo community_bank.sqlite.
  8. Resposta ao Cliente: O controller recebe o DTO de retorno e responde com status HTTP 201 Created com o payload contendo o cálculo da parcela mensal sem juros (R$ 250,00/mês) e taxa solidária de 0%.
Benefício Chave da Arquitetura: A regra de dependência de Robert C. Martin e Alistair Cockburn foi rigorosamente respeitada: nenhum arquivo do domínio (credit-request.ts, solidarity-enterprise.ts) ou da porta (ports/) importa bibliotecas do Express, SQLite ou qualquer recurso de infraestrutura externa.

6. Conclusão da Atividade

A atividade cumpriu integralmente todos os requisitos solicitados: o endpoint POST /credit/solidarity está operacional, o domínio protege as regras da moeda social e do microcrédito solidário, o caso de uso e as portas desacoplam os adaptadores, e a persistência relacional SQLite garante armazenamento durável em banco de dados real.
